Idea to live site, in order

Planning happens in one unbroken session. Building happens one ticket per fresh context. Shipping is always your call. Click any command to copy it.

The main flow

Four stages, run in this order for every feature.

1. Plan

one session
  1. Answer rounds of questions until nothing is assumed. Writes GLOSSARY.md and docs/adr/ as terms and decisions settle.
  2. Writes issues/spec.md from the grilling. Confirms the test seams with you first.
  3. Splits the spec into issues/NNN-*.md, each marked auto or HITL with its blockers. Approve the breakdown.

Don't /clear between these three. If context gets heavy, /compact after a step finishes.

2. Build

one ticket, or the queue
  1. then You build one ticket directly, commit, stop. Repeat per ticket.
  2. Works the queue: Sonnet coder builds, Opus reviewer checks risky changes. Stops at HITL gates and blockers. Run /triage-bugs first.

Each ticket: /tdd at the agreed seams, tests and typecheck, commit, move the ticket to issues/done/, note anything durable in CLAUDE.md.

3. Ship

when you say so
  1. Typecheck, tests, build and a secrets scan; then push to main, wait for the Vercel build, and check the production URL in Chrome.

Pushing is deploying. The build skills only commit locally; nothing reaches Vercel until you run /ship.

4. Look back

same session
  1. Suggests fixes to the setup, not the code: missing checks, CLAUDE.md pointers, skill tweaks. Most severe first.

Run it before you /clear, especially after a session that went sideways.

Rules of thumb

Tickets and the loop

  • auto builds with no human input. HITL has a gated step the build stops at: a decision, a review, or a manual step such as creating an account.
  • critical bugs jump the queue. Major and minor wait in the polish tier. When in doubt, minor.
  • One ticket per commit. Bugs found along the way get logged, never fixed in passing.
  • A ticket that won't fit in one fresh context is too big: split it in /to-tickets.
  • Tests go only at the seams agreed in the spec.

Vercel

  • Push to main deploys production; any other branch gets a preview.
  • Set env vars with the value piped in: printf '%s' "$V" | vercel env add NAME production. Pasting into the dashboard can store empty values that look correct.
  • Every env var goes in .env.example with a placeholder. Only that env file is committed.
  • Check the production alias, not the generated URL. On Hobby the generated URLs show an SSO page.
  • The alias can serve the old build for a few seconds after the deploy. Retry once before calling it broken.

New project, first time

  1. from the kit folder. Never overwrites existing files.
  2. Fill in the one-paragraph description at the top of CLAUDE.md.
  3. Create the GitHub repo and push the first commit.
  4. , then connect the repo under Settings → Git. Private repos need the Vercel GitHub App granted access.
  5. Env vars through /wizard or vercel env add; then vercel env pull for local dev.
  6. Start the main flow at /grill-with-docs.
